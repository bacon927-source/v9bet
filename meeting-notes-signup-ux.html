一、註冊（Sign Up）

1註冊方式 = 電話（預設分頁）／Email（分頁切換）＋密碼

  • 表單只有三件事：📱 Phone number｜✉️ Email 分頁 → 帳號欄位 → Password（👁 顯示切換）→ 21+/Terms 勾選。
  • 電話分頁輸入數字 → 彈出國碼選擇，只有 🇹🇭 泰國 +66 / 🇻🇳 越南 +84（依語系/geo-IP 預設）。在電話分頁貼上 email 會自動切到 Email 分頁。
  • 推薦碼移出註冊頁（原欄位由密碼取代）。
  • Account ID 放回註冊表單 → 最終（07-16 晚）：註冊表單不收 Account ID 也不收密碼——註冊只有 phone/email＋OTP。Account ID 改為系統自動產生（如 AHHHHHH）：個人資料唯讀顯示、忘記密碼 OTP 後顯示、已驗證 Email 也可當 Account ID；登入欄位仍接受 Account ID / Email / 電話。密碼改為選配：Setup Step 2「Set a password」（要用密碼登入才設）；沒設密碼就用一次性驗證碼／社群／Passkey 登入。
  • 版面（07-16）：Sign Up 頁社群 icon 移到最上方（同 Login 版式），下方「or sign up with」再接 Phone/Email 分頁；標題列互相連結——Sign Up 頁左上角放 Login 入口（✕ 移右上）、Login 頁右上角放 Sign Up 入口，兩頁底部的互連文字連結移除；Welcome 頁優惠卡移除 Claim now（改註記 auto-applied at first deposit，主 CTA 只留 Go to deposit）。
  • 21+/Terms 同意只有一處（07-16 最終）：社群 icon 下方那行說明移除，全部方式（電話／Email／社群）共用下面同一個勾選框；未勾選就點社群 icon → 提示先同意，勾選狀態即同意紀錄（時間戳＋條款版本）。Complete Setup 不再重複問，只剩幣別一項。

歷程：原本國碼+電話+推薦碼 → 改單一欄位自動判斷 → 最終定案加回明確的雙分頁（單一欄位邏輯保留在偵測行為）。

二、驗證（OTP / Verification）

4OTP 頻道 = Zalo ZNS / SMS / LINE / WhatsApp / Email

  • 預設依市場：VN = Zalo ZNS、TH = LINE；SMS 為通用備援；失敗 fallback = WhatsApp / Email。

5獨立 Verification Flow 頁面（07-16 新增，依 Unified OTP docx 對齊）

規格來源：《Unified OTP Authentication Flow Enhancement》docx。核心：系統分開維護 Email / 電話的驗證狀態（Verified / Not Verified），四種狀態決定 OTP 方式——無驗證→依動作而定、僅 Email→Email OTP、僅電話→Phone OTP、雙驗證→會員自選。

  • 適用 7 種動作：首次綁定、加另一種聯絡方式、改密碼、換綁 Email/電話、提款、領優惠、忘記密碼。
  • 同類型規則：改 Email 第一步 OTP 只能發到舊 Email（電話 OTP 不能代替）；改電話同理。新聯絡方式兩段 OTP 都通過才生效。
  • 無驗證聯絡方式：改密碼／提款 = 不允許；領優惠／首次綁定 = 現場輸入並驗證新聯絡方式後繼續。
  • 忘記密碼：不得在驗證成功前洩漏帳號是否存在；用於復原的聯絡方式不自動變 Verified（待業務確認）。
  • +10 points 獎勵（07-16）：首次綁定並驗證電話/Email 完成後獎勵 10 點——每人每種聯絡方式只發一次（防重複領取；換綁/重驗不再發），入帳記在 History 第 3 類（Rewards，08-30：Login & Devices 移出 History 後全部類別序號 -1）。
  • OTP 通則：有效 5–10 分鐘；系統需定義過期/錯誤上限/重發間隔/重發上限/失敗後動作/重用政策/信任期；OTP 綁定 會員+聯絡方式+動作+session；稽核日誌不存明碼。

5cOTP 設計稿對齊（07-16，dark theme mockups）

收到完整 OTP 元件視覺稿＋六個接入點，verification flow 已照此重寫。重點決議：

  • OTP 模式只有 Email / SMS（Select Verification Mode 單選）；Zalo ZNS / LINE / WhatsApp 遞送列為 phase 2。
  • 元件參數：6 位數碼、重發倒數 32 秒、錯誤顯示「Invalid OTP entered」（紅框紅鈕、倒數續跑）、第 3 次重發後冷卻升級 03:00、聯絡方式一律遮罩、支援 iOS 簡訊自動帶碼。
  • 無驗證聯絡方式 → 不再擋任何動作：所有入口（含改密碼、提款）都改為「現場輸入並驗證新聯絡方式，該驗證即當作 OTP」——覆蓋 docx 的 Not allowed。
  • 改密碼 = 2FA：移除舊密碼欄位，OTP 即身份驗證；改完強制重新登入。
  • 提款 OTP 觸發條件：收款帳戶（銀行帳號或 USDT 地址）首次使用時才要求 OTP。
  • 領優惠：先補 Personal Details（Full Name 需與銀行帳戶名完全一致＋生日）→ OTP → 繼續領取。
  • 忘記密碼：選模式（Email/SMS）→ 輸入註冊聯絡方式 → OTP 通過後才顯示 Account ID → 設新密碼（含強度計）；適用 Active / Dormant 帳號。
  • Profile 聯絡方式：首次輸入後電話移除自行編輯（未驗證狀態仍可 Edit）；換綁需先驗當前同類型聯絡方式，收不到碼 → 找客服；「Verified Email may be used as Account ID」。

QQ&A：拿掉密碼後，怎麼用密碼登入？（07-16，含後續修正）

密碼是選配——要等客人在 Setup Step 2「Set a password」或之後在 Profile & Settings › Change password 主動設定，密碼登入才會存在。

第一版做法：Password 分頁偵測到沒設密碼時，主動顯示「No password set yet」提示 + 導去設定 → 使用者指出安全問題後撤回：登入前系統本來就不該知道、也不該告訴使用者「這個帳號有沒有密碼」——那等於在驗證前洩漏帳號存在與其驗證方式，跟 Forgot Password 早就定案的「不洩漏帳號是否存在」是同一個道理。

  • 最終做法：Password 分頁沒有特殊提示畫面；沒設密碼的人用 Password 登入，一律當成一般的 INVALID_CREDENTIALS 失敗處理，不特別說明原因。
  • 不會卡住：One-time code／Passkey／社群登入永遠可用，密碼要不要設、什麼時候設，客人自己去 Settings 決定，系統不主動提醒。
  • 三個檔案（signup-flow、login-flow、full-wireframe）的 Login 畫面已還原為原本 3～4 個狀態，不含「none set yet」。

R社群登入配對到既有帳號 —— 改成先驗證既有帳號才綁定（08-30）

原本 Google 登入配對到既有帳號（Account Found）時，「Bind and login」按一下就直接登進去——只靠 Google 這一邊的驗證。查了市場作法（Auth0 account linking／Google Identity Platform 的 account-exists-with-different-credential）後改掉：兩邊都要各自證明身分才能綁定，不是新身分驗證過就夠。

  • Account Found → 「Send code to existing account」（發 OTP 到既有帳號留底的手機）→ 輸入正確 → 才真正綁定＋登入（Welcome back!）。
  • 配對規則：只跟既有帳號已驗證的 email/phone 比對——沒驗證過的聯絡方式不會觸發配對，避免有人在閒置帳號填別人的 email，等真正的擁有者用 Google 登入時被劫持。
  • 新帳號（沒有配對到既有帳號）仍然維持原本「無需 OTP」——Google 已經驗證過那個新身分了。

TSetup／Login 拿掉「Simple PIN」選項（08-30）

原本 Setup Step 2「Password / PIN」讓客人二選一當帳號登入方式，4 位數 PIN 只有一萬種組合，拿來當一個博弈/金流帳號的登入密碼太弱——這是原始 docx「Set account password or simple pin」直接照搬的問題。

  • 移除：帳號登入安全只剩 Password（選配）＋ Face ID / passkey 兩種，畫面改名「Set a Password」。
  • 之後如果真的要做「快速解鎖」，應該放在裝置/App Lock 那層（跟 Face ID 同級）——只能打開 App，不能拿來登入或授權提款/改安全設定這類敏感動作。
  • 已同步：signup-flow-wireframe、v9bet-full-wireframe（含 Login 畫面本身也移除 PIN state，跟 login-flow-wireframe 對齊）、v9bet-flows-composition。

UFace ID / passkey：mandatory 字樣跟 can-skip 獎勵制矛盾（08-30）

問 passkey 實際怎麼運作時發現：Setup 這個項目的分組標記寫「Step 2 · Security (can skip)」、也算 +10 pts 獎勵項目，但 spec goal／notes 卻原封不動抄 docx 原文「mandatory」——兩邊互相矛盾。裁定：can skip，跟現有的 9 項 ×10pts 獎勵制一致；已更新 signup-flow-wireframe、v9bet-full-wireframe 的 spec 文字，拿掉「mandatory」字樣。

順便記一個技術筆記：這個項目名稱把「App 生物辨識解鎖」（本機用臉/指紋開啟既有 session，換新裝置沒用）跟「Passkey／WebAuthn」（真正註冊到伺服器的公私鑰憑證，透過 iCloud 鑰匙圈/Google 密碼管理員可以同步到新裝置登入）混成一個開關。目前先不拆——如果之後真的要做「passkey 跨裝置登入」這個功能，才需要把兩者分開存欄位。

V單一裝置登入 —— 「Login sessions」列表不寫實（08-30）

使用者指出：我們只能允許一台裝置登入，Security 頁那個「3 active / 2 active」多裝置清單（可以個別 Log out）不寫實——同時也確認 History 的登入紀錄本來就該是多筆歷史紀錄（3 筆以上），這兩件事不衝突：一個是「現在同時有幾台裝置在線」（只能 1），一個是「過去登入過幾次」（本來就會很多筆）。

  • Security & Sessions（profile-settings-flow-wireframe／v9bet-full-wireframe「Account Security」）：「Login sessions · N active」改成「Active session · This device」，子畫面拿掉多裝置清單，只顯示目前這一台 ＋ 最近幾筆登入記錄（唯讀）。＋「Log out this device」（手動強制登出，掉手機時可用） → 這顆按鈕後來（08-30，見下方 Z）也被拿掉了——邏輯上做不到它宣稱的事。
  • Login（login-flow-wireframe）：任何方式登入成功，都會自動結束另一台裝置的 session（伺服器強制），不會出現確認畫面——被登出的那台就是直接掉線；這個事件本身會被記一筆「Logout · ended by new login」進 History。
  • 掉手機的復原流程也跟著簡化：新裝置登入本身就會自動結束舊裝置的 session（不用再手動去 Login sessions 裡登出），唯一還需要手動做的是去 Passkey · Manage 撤銷舊裝置那把 passkey（session 結束不會連帶撤銷 passkey）。

後續追問「3 筆歷史記錄要放哪」（08-30）：使用者確認乾脆整組併進 Settings，History 拿掉「Login & Devices」這個獨立分類——登入/裝置記錄從此只存在於 Profile & Settings › Security & Sessions 一個地方，不再跟 History 重複。History 的 8 大分類變成 7 類，原本 2–8 類（Deposits/Withdrawals…Responsible Gaming）序號各 -1（現為 1–7）；所有引用舊分類編號的地方（promotion-flow、growth-support、verification-flow、profile-settings 的 spec notes，以及本記錄前面第 5 條）都已同步改號。

Z拿掉 Active Session 的「Log out this device」——邏輯講不通（08-30）

使用者問：只允許一台裝置登入，我登入了要 logout 誰？——問到重點：既然單一裝置政策下你能看到這頁，代表你就是那唯一一台在線的裝置，「Log out this device」只可能把你自己現在登出，跟 Settings Home 本來就有的「Log out」沒兩樣。原本寫的「掉手機時可用、在你去別的地方登入之前就先登出」也站不住腳——你不可能在還沒登入任何裝置的情況下看到這個畫面，而你能看到這頁，就代表新裝置登入已經自動把舊裝置踢了。

  • 拿掉這個按鈕跟它的提示文字，Active Session 這頁改成純唯讀：目前這台裝置 + 最近登入記錄。
  • 掉手機的復原邏輯不變（新裝置登入就會自動結束舊裝置 session），只是不再假裝有一個額外的「手動登出別的裝置」按鈕——那個按鈕從頭到尾都做不到它宣稱的事。
  • 已同步 profile-settings-flow-wireframe.html、v9bet-full-wireframe.html「Account Security」。
