註冊雙軌流程

Two Registration Tracks
三條路徑共用同一個註冊頁：我們自己的 Email 註冊、第三方登入，以及一年後回來的休眠帳號。前兩條建立新帳號、在 Setup 合流；第三條不建立帳號，也不重跑 Setup。最後回答「第三方會員要不要再補 email」。
Three paths share one sign-up screen: our own email registration, social login, and a dormant account returning after a year. The first two create an account and merge at Setup; the third creates nothing and skips Setup entirely. The decision on whether social members must still add an email follows at the end.

1

填註冊頁

Fill in the sign-up screen
Email 必填、Referral code 選填、21+ 與條款必勾。沒有密碼、沒有 Captcha、不用自己取 Account ID。
Email required, referral code optional, 21+ and Terms must be ticked. No password, no Captcha, no member-chosen Account ID.
2

送出 → 寄出 6 位數驗證碼

Submit → a 6-digit code is sent
POST /register/start
新 email 和既有 email 都會寄碼，差別只在回應——這樣才不會讓人從「有沒有寄」反推帳號存不存在。
A code goes out for both new and existing addresses; only the response differs. Otherwise the presence of an email would itself reveal whether an account exists.
3

依 email 是否已註冊分岔

Branches on whether the address is already registered
  • 全新 email → OTP Verification 畫面。6 位數、32 秒可重寄、第 3 次後冷卻 03:00。過程中不能改 email，打錯要關掉重來。
    New address → OTP Verification screen. Six digits, resend after 32s, cooldown rises to 03:00 after the third resend. The address cannot be edited mid-flow — a typo means closing and starting again.
  • 已有帳號 → 置中 modal「The account already exists」。驗證碼直接在 modal 裡輸入，不跳頁，通過即登入。
    Existing account → a centred modal, "The account already exists". The code is entered inside the modal — no navigation — and passing it logs the member in.
  • 限流必做 — 既有帳號會被明講，所以要依 email 和 IP 各自限流，否則可被拿來批次查 email 是否註冊過。
    Rate limiting is mandatory — since an existing account is named openly, throttle per address and per IP, or this endpoint becomes a way to test addresses in bulk.
4

驗證通過 → 帳號建立

Code accepted → account created
Account ID 自動產生。帳號手上已經有一組已驗證的 email，缺的是電話（Setup Step 2 才補）。
Account ID is generated automatically. The account already holds one verified email; what it lacks is a phone, added later in Setup Step 2.
若是既有帳號：休眠且無違規 → 原地重新啟用；正常 → 直接登入；受限 → 只給 Live Chat，不說原因。
For an existing account: dormant and clean → reactivated in place; active → simply signed in; restricted → Live Chat only, with no reason given.
Track B
第三方註冊
Social sign-up
Google ／ LINE ／ Zalo
Google / LINE / Zalo
1

點社群 icon

Tap a social icon
21+ 與條款同樣要先勾——勾選框是所有註冊方式共用的，沒勾就點 icon 會先提示。
The 21+ and Terms checkbox applies here too — it is shared by every sign-up method, and tapping an icon while unticked prompts for consent first.

All providers go through the central verification domain auth.<stable>, so rotating public mirrors never breaks OAuth.
2

Provider 授權

Provider consent
Google One Tap ／ LINE ／ Zalo 的同意畫面，沒有站內轉跳頁。取消或失敗就回註冊頁。
The provider's own consent screen (Google One Tap / LINE / Zalo) — there is no in-app redirect screen. Cancelling or failing returns to sign-up.
3

交換 token → 三種結果

Exchange the token → three outcomes
POST /auth/social/exchange
  • 全新帳號 → 不需要 OTP，直接進 Welcome。provider 已經證明過身分了。
    Brand-new account → no OTP, straight to Welcome. The provider has already proved the identity.
  • 配對到既有帳號 → Account Found，詢問是否綁定。驗證碼寄到既有帳號已驗證的聯絡方式，不是新的 provider——兩邊都要證明身分才綁。
    Matches an existing account → Account Found, offering to link. The code goes to the contact on file for the existing account, not to the new provider — both sides must prove themselves before linking.
  • 既有帳號本身沒有聯絡方式 → 沒有地方可以寄碼，只能導 Live Chat。
    The existing account has no contact at all → there is nowhere to send a code, so this case falls through to Live Chat.
4

帳號建立 → 但手上有什麼，看 provider

Account created — but what it holds depends on the provider
這是兩條路徑最大的差別：Email 註冊一定有 email，第三方註冊不一定有。詳見下一節。
This is the biggest difference between the two tracks: an email sign-up always has an email; a social sign-up may not. See the next section.
Track C
一年後回來（登入）
Coming back after a year — a login
休眠帳號重新啟用。這是登入，不是註冊——沒有建立任何帳號。
Reactivating a dormant account. This is a login, not a registration — nothing is created.
1

兩個入口都會通

Either entry point works
可以走 Login，也可以又跑去 Sign Up 填舊 email——很多人真的會以為要重新註冊。兩條都導到同一個地方，不會產生第二個帳號。
They can use Login, or go to Sign Up and enter their old address — many people genuinely assume they must register again. Both routes land in the same place, and neither creates a second account.
2

驗證碼通過前，什麼都不透露

Nothing is revealed until the code passes
走 Sign Up 的話，看到的是同一個「The account already exists」modal 和同一組 6 位數驗證碼。帳號是休眠、正常還是被限制，在這一刻完全看不出來。
Via Sign Up they meet the same "The account already exists" modal and the same 6-digit code. Whether the account is dormant, active or restricted is indistinguishable at this point.
3

通過後才分三種

Only then does it branch three ways
  • 休眠且無違規 → 原地重新啟用。餘額、紀錄、等級、收款帳戶全部保留，什麼都不會被重設。埋點送 login 並帶 reactivated，不是 sign_up。
    Dormant and clean → reactivated in place. Balance, history, tier and payout accounts all carry over; nothing is reset. The event is login with reactivated, never sign_up.
  • 其實一直是正常帳號 → 直接登入，不會建立第二個帳號。
    Actually still active → simply signed in, with no duplicate account created.
  • 受限（自我排除、RG 封鎖、合規凍結）→ 只給 Live Chat，不說原因、沒有自助管道。自我排除的人最先會試的就是重新註冊，這條路必須是死路。
    Restricted (self-exclusion, RG block, compliance hold) → Live Chat only, with no reason given and no self-service route. Re-registering is the first thing a self-excluded member tries, so this path has to be a dead end.
4

回來之後會撞到的事

What a year away actually changes
不用重跑 Setup——一年前已經做完了。但有幾件事跟新會員不一樣：
Setup is not repeated — it was completed a year ago. But several things differ from a new member:
  • History 前台只顯示最近 30 天，所以一年前的紀錄這裡看不到，要走 Export CSV。
    History only shows the last 30 days in the front end, so a year-old record is not visible there — it comes out via Export CSV.
  • 收款帳戶還在，但第一次提款到任何帳戶仍要 OTP，回來後的第一筆提款會被要求驗證。
    Payout accounts survive, but a first withdrawal to any account still triggers OTP, so the first payout after returning will ask for one.
  • 幣別當年就鎖定了，回來也不能改。
    Currency was locked at the time and still cannot be changed.
  • 舊裝置的 passkey 不會因為長期沒登入而失效——換了手機要自己到 Settings › Passkeys 撤銷。
    A passkey on the old device does not expire through inactivity — after changing phones it must be revoked in Settings › Passkeys.
  • 邊界情況：當年如果沒做完 Step 1 就跑了，回來還是得補完才能存款或遊戲。
    Edge case: if they abandoned before finishing Step 1 a year ago, they still have to complete it before depositing or playing.

你提的：Welcome 後面不用再補 email

The proposal: drop the add-an-email step after Welcome
前提是「第三方註冊通常都帶 email」。這個前提有一半成立——下面是採用的結果。
The premise was that social sign-ups usually carry an email. That premise holds for half the providers — here is how it was resolved.

成立的部分 · Where it holds

Google 註冊確實不該再問一次 email。帳號已經有一組經過驗證的信箱，再叫人填一次是純粹的多餘步驟。
A Google sign-up genuinely should not be asked for an email again. The account already holds a verified inbox; asking twice is pure redundancy.
  • 目前 Welcome 頁分成兩種版本，本身就是「夾帶在裡面」的來源
    The two Welcome variants were themselves the source of the tangle.
  • Google 會員看到補 email 的提示，只會覺得系統不記得他剛做過什麼
    To a Google member, that prompt reads as a system that forgot what they just did.

不成立的部分 · Where it breaks

Zalo 不給 email，LINE 要申請才有。如果整個拿掉，這些會員的帳號會是零聯絡方式。
Zalo returns no email, and LINE only does with an approved permission. Removing the step outright would leave those members with no contact at all.
  • 收不到 OTP → 提款做不了（第一次用的收款帳戶一定要 OTP）
    No OTP means no withdrawals — a first-time payout account always requires one.
  • 收不到任何通知與存提款狀態
    No notifications and no deposit or withdrawal status can reach them.
  • 社群帳號掉了 → 沒有自助救回管道，只能走 Live Chat
    Losing the social account leaves no self-service recovery — only Live Chat.

順帶一提，現在已經有個洞 · A gap that already existed

Contact Details 原本排在 Step 2（可跳過）。也就是說就算保留這個步驟，Zalo 會員照樣可以一路跳過，最後一樣得到零聯絡方式的帳號。這個洞在提案之前就存在。
Contact Details previously sat in Step 2, which is skippable. So even with the step kept, a Zalo member could skip straight past it and still finish with an unreachable account. This gap pre-dated the proposal.

已實作：用一條規則取代兩種 Welcome

Implemented: one rule replaces the two Welcome variants
不看「註冊方式」，改看「帳號現在有沒有已驗證的聯絡方式」（has_verified_contact）。這一條規則同時做到你要的效果、而且把上面那個洞關掉。
The test is no longer which method was used, but whether the account currently holds a verified contact (has_verified_contact). One rule delivers the requested behaviour and closes the gap above.
有聯絡方式 · Has a contact

Email 註冊、Google、LINE（若拿到權限）

Email sign-up, Google, LINE with the permission
Welcome 之後直接進 Setup，補 email 的步驟完全不出現——就是你要的結果。
Welcome leads straight into Setup and the add-an-email step never appears — exactly the requested outcome.
沒有聯絡方式 · No contact

Zalo、LINE（沒拿到權限）

Zalo, LINE without the permission
「補一個聯絡方式」成為 Step 1 必填，跟幣別、收款帳戶放在一起，而不是掛在 Welcome 上當按鈕。
"Add an email or phone" becomes a required Step 1 item, sitting alongside currency and payout account rather than hanging off Welcome as a button.
好處是三件事一次解決：多數會員不再看到多餘步驟、Welcome 頁只剩一種版本、零聯絡方式的帳號被擋在 Setup 就補起來。
Three things resolve at once: most members stop seeing a redundant step, Welcome collapses to a single variant, and contactless accounts are caught at Setup instead of slipping through.

仍待業務確認 · Still open for the business

  1. 要不要去申請 LINE 的 Email address permission？這決定 LINE 會員落在哪一邊。規則本身不受影響——拿到權限後 LINE 會自動走「有聯絡方式」那條，不用改任何畫面。
    Should the LINE Email address permission be applied for? It decides which side LINE members land on. The rule itself is unaffected: once granted, LINE moves to the "has a contact" path on its own, with no screen changes.
  2. Zalo 會員補的是 email 還是電話？目前畫面問的是 email。越南市場用電話可能更自然，但每次 OTP 都有 SMS 成本。若要改，Contact Details 需要再加一個必填變體。
    For a Zalo member, should the required contact be an email or a phone? The screen currently asks for an email. A phone may feel more natural in Vietnam but carries an SMS cost per OTP; switching would need a second required variant of Contact Details.
已完成：Welcome 併為單一版本、聯絡方式項目在無聯絡方式時移入 Step 1 必填、該變體移除 Later 連結。三處 Dev Notes 都已記錄推翻原因與日期。
Done: Welcome merged into one variant, the contact item promoted into required Step 1 when no contact exists, and the Later link removed from that variant. All three sets of Dev Notes record the reversal and its date.
